Problem Definition
Problem Definition & Architecture Decision
~Weeks
Task Definition
Given a context window of historical time series values, forecast the next H future values.

Works on any domain without retraining — zero-shot.
Key Design Decision
Foundation model approach (train once, generalize) vs. traditional per-dataset specialized models (ARIMA, N-BEATS, N-HiTS).

Bet: a large model on diverse data beats small specialized models.
Input / Output Contract
Input 512 historical time steps (any domain, any frequency)

Output Probabilistic forecast: point + quantiles (p10, p50, p90)

No labels Self-supervised on historical data only
PM Decision Point: Choosing "foundation model" over specialized models is a bet on transfer learning across time series domains (stock prices, CPU metrics, web traffic, weather). The cost is 10–100× more training compute. The return is zero-shot generalization — no per-domain labeling or retraining.

Tokenization
Tokenization — Patch-Based Time Series Encoding
Architecture Choice
The Patching Approach
Time series values → fixed-length patches of 32 steps each.

Each patch → single embedding vector via linear projection.

Identical concept to Vision Transformer (ViT) image patching — just applied to 1D sequences instead of 2D images.
Why Patching?
Problem 512 raw values → 512 tokens. Attention is O(N²). Very expensive.

Solution 512 values ÷ 32 per patch = 16 tokens.

Each token captures local temporal patterns (trend within a patch).
Normalization Layer
Each patch independently normalized (subtract mean, divide std).

Why: allows the model to learn patterns agnostic to scale — a CPU metric (0–100%) and stock price ($100–$500) should use the same model weights.

Reversible norm — scale restored at output
PM Decision Point: Patching is the tokenization equivalent of subword BPE for text — it reduces sequence length (cheaper attention) while preserving enough local structure. The patch size (32) is a hyperparameter: smaller patches = more detail but more tokens; larger patches = coarser representation.

PM Decision Point: Why decoder-only? Because forecasting is generative — you're generating future values conditioned on past values. This maps directly to the LLM autoregressive paradigm. Encoder-only (BERT-style) would give you representations but no generation. Encoder-decoder (T5-style) is heavier and adds no benefit when input and output are the same modality.

Pretraining
Pretraining — Self-Supervised Forecasting Objective
Weeks on TPU v4
Training Objective
Not cross-entropy (no discrete tokens).

Quantile Loss: for each forecast horizon, the model predicts multiple quantiles (p10, p50, p90). Loss = weighted sum of pinball losses across quantiles.

This trains probabilistic forecasting — the model learns uncertainty, not just point estimates.
Training Setup
Hardware Google TPU v4 pods
Data 100B time points (~5B training windows)
Batch size Large (thousands of windows per step)
Optimizer Adafactor (memory-efficient Adam variant)
Mixed precision BF16
Scaling Law Consideration
200M parameters is small by LLM standards but large for time series.

Chinchilla-optimal at 200M ≈ 4B training points. Google used 100B points → ~25× over-trained relative to Chinchilla.

Why: inference is cheap (serving millions of forecasts); over-training yields a better small model.
PM Decision Point: The quantile loss objective is a strategic product decision — it forces the model to produce calibrated uncertainty estimates, not just point predictions. For monitoring use cases (Splunk, ops), knowing "the model is 90% confident this won't exceed threshold X" is far more actionable than just a point forecast. Uncertainty = confidence interval = actionability.

Fine-Tuning & Adaptation
Fine-Tuning & Domain Adaptation
Hours–Days
Full Fine-Tuning
Update all 200M parameters on domain-specific time series.

Use case: proprietary datasets with unique patterns (custom financial instruments, internal SLA metrics)

Requires: 10K+ series, significant domain data. Cost: hours on a single GPU.
LoRA Adaptation
Freeze backbone. Add low-rank adapters to attention layers.

Use case: specific industry domains (healthcare vitals, energy grids, Splunk log anomaly rates)

Requires: 1K+ series. Cost: minutes to hours. Storage: <10MB per adapter.
Zero / Few-Shot
No fine-tuning. Use pretrained model directly.

Works for: most standard time series (web traffic, IoT sensors, business metrics)

Baseline: this is TimesFM's primary product proposition — no per-customer training needed.
No RLHF Needed
Unlike LLMs, time series models don't need RLHF. The task has a ground truth (actual future values) — no ambiguity about "what's a good forecast."

The quantile loss is the objective alignment — no human preference labeling required.
Splunk Application
LoRA fine-tune on Splunk-specific metric patterns:
· Error rate time series
· CPU/memory utilization patterns
· Network anomaly signals
· Alert frequency series

Domain adapter: <10MB, per-customer.
Catastrophic Forgetting Guard
When fine-tuning on a specific domain, validate on the original zero-shot benchmarks to ensure generalization hasn't degraded.

Same principle as LLM fine-tuning — narrow data can overwrite general capabilities.
PM Decision Point: The "no RLHF" point is significant for product roadmap. TimesFM's alignment problem is solved by the training objective itself (quantile loss + ground truth). This makes the development cycle faster — no labeling pipeline, no reward model, no PPO. Budget accordingly.

Cost at Scale
1M forecast calls/day:
· Vertex AI: ~$0.001–0.005 per call
· Self-hosted A100: $2–3/hr → millions of forecasts per dollar

Key insight: small model = affordable at massive scale
PM Decision Point: TimesFM's 200M parameter size is a deliberate product decision — it makes self-hosting economically viable for any company. GPT-4 size would make per-forecast costs prohibitive for high-frequency monitoring (Splunk processes billions of events daily). Smaller model + purpose-built = the right call for this use case.

Monitoring & Feedback Loop
Production Monitoring & Closed-Loop Improvement
Continuous
Production Quality Signals
Forecast accuracy Track MAE/MASE on live data as actuals become available

Calibration Are p10/p90 quantiles actually covering 10%/90% of actuals?

Drift detection Monitor when model accuracy degrades — signals distribution shift in incoming data
Data Flywheel Opportunity
Every forecast call generates a (context, forecast, actual) triple once the future arrives.

This is labeled training data — for free.

Production actuals → new training examples → improved model. The more the model is used, the better it gets.
When to Retrain
Trigger 1 MAE degrades >10% from baseline on live data
Trigger 2 New data domain added (e.g., new sensor type)
Trigger 3 Calibration drift (quantile coverage off by >5%)
Trigger 4 Scheduled: quarterly model refresh
PM Decision Point: Defining retraining triggers is a product decision, not just an engineering one. Retraining costs money and time. Triggers too tight = expensive continuous retraining. Triggers too loose = degraded product quality that users notice before you do. These thresholds belong in the product spec, not just the ops runbook.

Stage 2 — Data
Splunk's moat is customer log + metric data at massive scale. The data flywheel is already there — it just needs the pipeline to convert forecasting errors into new training examples.
Stage 3 — Tokenization
Log events are already time-indexed. Patch-based tokenization maps directly to Splunk's bucket/window aggregation model. No novel tokenization needed — reuse TimesFM's patching.
Stage 6 — Evaluation
For security time series (alert rates, error spikes), calibration (correct quantile coverage) matters more than raw MAE — a model that gives accurate confidence intervals lets analysts prioritize alerts correctly.
Stage 7 — Fine-Tuning
LoRA adapters per customer cluster type (cloud-native, on-prem, hybrid). Start from TimesFM's open weights, fine-tune on Splunk-specific patterns. 10MB per customer adapter = viable at enterprise scale.
